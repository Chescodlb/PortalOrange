1. Alcance, responsables y decisión inicial

Manual para añadir Portal Orange al campus de producción o actualizar una instalación Orange existente. Referencia: Moodle 4.5.1, local_orangeportal 2026111007, theme_orange 2026102900, base 9ea45bb más el configurador CLI de esta entrega. No incluye actualización de PHP, Moodle ni MySQL.

ResponsableTrabajo
SistemasRespaldo, copia de directorios, actualización de Moodle, permisos de archivos, PHP CLI, cron y conectividad HTTPS.
Administrador general de MoodleCategorías raíz, cohorte Orange, tema por cohorte, ajustes del portal, roles y Teams.
Administrador OrangeCuentas y colectivos dentro de Orange; verificación de contenido y seguimiento.
FormaciónCarga o revisión de documentos, cursos, actividades, destinatarios y publicación.
Responsable de Power AutomateURL de producción, conexiones, destino Teams e historial del flujo.
  1. Identificar si producción no tiene todavía Orange o ya contiene categorías, usuarios y publicaciones Orange.
  2. Si es una primera instalación, seguir todos los capítulos y escoger una única vía para la estructura: importación por consola o creación manual desde Moodle.
  3. Si Orange ya tiene datos, actualizar el código y conservar los datos existentes. No ejecutar el importador inicial ni recrear raíces, cohortes o roles que ya existan.
  4. Confirmar con el cliente qué estructura, contenidos y perfiles se han validado en pre antes de promoverlos.

Copiar directorios de código no copia categorías, cursos, documentos, usuarios ni lecturas. Los IDs de pre no se reutilizan como IDs de producción. No se copia la base de datos de pre sobre el campus de producción.

RAIZ_MOODLE significa la carpeta que contiene config.php. /var/www/moodle se utiliza como ejemplo en este manual. No deben quedar carpetas duplicadas, como local/orangeportal/orangeportal/.

El JSON que acompaña este manual es la referencia del 22 de octubre de 2026 disponible en el proyecto, no una exportación automática del estado actual de pre. No cargar todo el repositorio, .env, config.php de otro entorno, moodledata de pre, contraseñas de demo, scripts de prueba ni las carpetas Postman como contenido web. Los cli/check_* incluidos en el plugin son pruebas locales, no órdenes del pase a producción.

3. Preparación del servidor y respaldo

  1. Anotar dominio del campus de producción, raíz Moodle, moodledata, usuario de servicio, versión de PHP CLI y mecanismo de cron existente.
  2. Inventariar versiones del plugin y de Orange/Moove; guardar la configuración del tema general y la portada del campus.
  3. Realizar un respaldo consistente de base de datos, código y moodledata mediante el procedimiento de Sistemas. Anotar ubicación y método de restauración.
  4. Guardar las configuraciones Orange existentes, IDs de raíces, cohorte base, catálogos y roles si ya existe Orange.
  5. Confirmar la ventana de despliegue y el estado del cron: coordinar el procesamiento de tareas durante mantenimiento para que no use archivos parcialmente copiados.
  6. Confirmar URL y destino de Teams de producción. Las pruebas y cargas no deben usar accidentalmente un flujo de otro ambiente.

Sistemas identifica PHP en el entorno que ejecuta Moodle, con el usuario de servicio correspondiente:

command -v php

Los ejemplos siguientes usan php para facilitar la lectura. Si el servidor necesita una ruta absoluta, utilizar la devuelta por Sistemas. No se instala ni cambia la versión de PHP como parte de este pase.

4. Instalar el código: consola o interfaz de Moodle

Vía A, consola y copia de archivos: desde la raíz real de Moodle, con el usuario de servicio del campus:

cd /var/www/moodle
php admin/cli/maintenance.php --enable
  1. Sistemas copia los directorios de esta entrega en local/orangeportal y theme/orange. Moove solo se instala si falta o según la versión aprobada.
  2. Conservar propietario y permisos habituales del servidor; el usuario de PHP debe poder leer el código.
  3. Ejecutar la actualización y limpiar cachés. Revisar la salida antes de continuar.
php admin/cli/upgrade.php --non-interactive
php admin/cli/purge_caches.php

Vía B, instalador web: si el alojamiento y la política del campus permiten instalar complementos por la web:

  1. Entrar como administrador general. En Servidor → Modo de mantenimiento, habilitar mantenimiento durante la intervención.
  2. Usar Administración del sitio → Plugins → Instalar plugins para cargar cada ZIP del componente, solo si esa función está habilitada y el servidor tiene los permisos necesarios.
  3. Si falta Moove, instalar primero la distribución aprobada de Moove, después local_orangeportal y después theme_orange. Si Moove ya existe, revisar compatibilidad antes de tocarlo.
  4. Seguir Administración del sitio → Notificaciones hasta completar todas las actualizaciones y guardar los ajustes nuevos que Moodle solicite.
  5. Purgar cachés desde Desarrollo → Purgar todas las cachés.

Si la instalación web está deshabilitada o no permite reemplazar un componente existente, Sistemas debe copiar los directorios. No hay que desinstalar el plugin para actualizarlo: desinstalar puede eliminar sus datos.

El instalador crea o actualiza las tablas y permisos propios. La revisión 2026111006 no añade tablas respecto a 2026111005; una instalación más antigua sí puede ejecutar migraciones previas.

Al terminar la actualización del código, retirar mantenimiento para continuar las verificaciones funcionales, si el procedimiento de publicación del campus lo permite. Mantener Orange sin usuarios finales hasta validar su configuración:

php admin/cli/maintenance.php --disable

Alternativa web: desactivar mantenimiento en Servidor → Modo de mantenimiento. Si falla la actualización, conservar mantenimiento y resolver o restaurar el respaldo antes de abrir el campus.

5. Configuración automática: sin alternar consola y portal

Desde 2026111007 se puede completar la configuración inicial desde un archivo privado. Los capítulos posteriores de configuración web se conservan como alternativa y referencia de comprobación; no hay que intercalarlos en esta vía.

  1. Copiar el código actualizado y ejecutar la actualización de Moodle.
  2. Preparar configuracion-orange.json a partir de la plantilla entregada, fuera del directorio web y con permisos restringidos. Completar site_url con la URL exacta del campus y php_cli con la ruta comprobada por Sistemas.
  3. Para una instalación nueva, utilizar las definiciones de raíces y cohorte con Número ID y create=true. El script las resuelve o crea y configura sus IDs sin buscarlos en la interfaz.
  4. Para una actualización existente, conservar los IDs o Números ID actuales y dejar catalog_file en null. No crear otra estructura ni activar allow_scope_change por rutina.
  5. Si es una primera carga aprobada, poner catalog_file a la ruta privada del JSON. Se importa dentro de la misma operación y repetir el mismo archivo no duplica el catálogo.
  6. Guardar la URL completa de Teams en un archivo privado y referirlo con teams.url_file. Si se va a activar, definir teams.enabled como true. Si se omite el archivo, se conserva la URL existente; la plantilla inicia Teams desactivado.
  7. Si procede, indicar en administrators los nombres de usuario ya existentes que deben ser administradores Orange. El script añade audiencia y rol restringido sin crear cuentas ni cambiar contraseñas.
  8. Ejecutar validación y después --apply. Leer la salida, que oculta la credencial. Purgar cachés.
  9. Sistemas verifica o configura cron cada minuto dentro del mismo pase. No se necesita la interfaz Moodle para programarlo. El configurador no ejecuta cron ni envía mensajes.
php admin/cli/upgrade.php --non-interactive
php local/orangeportal/cli/configure.php --file=/ruta/privada/configuracion-orange.json
php local/orangeportal/cli/configure.php --file=/ruta/privada/configuracion-orange.json --apply
php admin/cli/purge_caches.php
Ajuste del archivoResultado

El script ejecuta las sincronizaciones de ámbito y permisos que necesita Orange, además de guardar variables. Repetirlo no duplica recursos. Una discrepancia con site_url, config.php, recursos o un catálogo existente se rechaza antes de aplicar.

No crea cuentas, no importa todos los perfiles XML ni carga documentos/cursos. Estas cargas siguen su procedimiento específico. La comprobación funcional final se realiza desde el portal después de terminar la configuración por consola.

6. Crear o identificar las raíces de Biblioteca y Formaciones

  1. Abrir Administración del sitio → Cursos → Administrar cursos y categorías.
  2. Si es una primera instalación, crear una categoría raíz Biblioteca Orange y otra Formaciones Orange, en un ámbito exclusivo del proyecto. El nombre visible puede adaptarse; Orange no es obligatorio en el nombre.
  3. Si se utilizará el importador JSON, establecer Número ID de Biblioteca a orange_pre_library y Número ID de Formaciones a orange_pre_training.
  4. Abrir cada categoría y anotar su ID numérico en la URL. No confundirlo con Número ID, que es un texto técnico.
  5. Si ya existe Orange, identificar sus raíces actuales y conservarlas. No crear categorías paralelas ni mover contenidos de otros proyectos.

Las raíces deben estar vacías para importar. Si se elige la carga manual del capítulo 7, estos Números ID específicos no son necesarios.

7. Cargar la estructura por consola: solo primera instalación

Si se ha usado configure.php con catalog_file, esta carga ya está hecha y no se debe repetir. Esta vía utiliza el JSON de referencia. No se combina con crear previamente las mismas subcategorías o catálogos a mano.

  1. Sistemas guarda catalogos-orange.json fuera del directorio público, en una carpeta legible por el usuario de servicio.
  2. Confirmar raíces vacías y Números ID correctos. Confirmar que no existen categorías/publicaciones de Incidencias o Comunicados ni catálogos de estados/impactos guardados.
  3. Sustituir /ruta/privada/catalogos-orange.json, ID_BIBLIOTECA e ID_FORMACIONES en el comando. No ejecutar los marcadores literalmente ni copiar los IDs de pre.
  4. Ejecutar primero sin --apply: valida y no escribe.
  5. Revisar el resumen con el inventario aprobado. Si coincide, ejecutar el mismo comando con --apply.
  6. Limpiar cachés y comprobar las categorías desde Moodle.
php local/orangeportal/cli/import_preproduction.php --file=/ruta/privada/catalogos-orange.json --library-root-id=ID_BIBLIOTECA --training-root-id=ID_FORMACIONES
php local/orangeportal/cli/import_preproduction.php --file=/ruta/privada/catalogos-orange.json --library-root-id=ID_BIBLIOTECA --training-root-id=ID_FORMACIONES --apply
php admin/cli/purge_caches.php
Referencia del JSON entregadoResultado esperado
Biblioteca167 subcategorías; 168 categorías contando su raíz. Incluye RPV y CENTREX.
FormacionesFormación inicial y Formación continua: dos subcategorías, además de la raíz.
IncidenciasCinco categorías con su jerarquía: Red móvil y Sistemas → Centrex → Alta → Sin Terminal.
ComunicadosUna categoría: Comunicado.
Estados e impactosSe cargan nombres, códigos y activación del JSON; revisar el capítulo 8.

El script se llama import_preproduction.php por su origen, pero trabaja sobre la instalación que lo ejecuta. No crea cuentas, documentos, cursos, matrículas, ajustes del portal ni temas. Rechaza una segunda carga o datos existentes. No borrar contenido para forzar su ejecución.

Desde el portal no hay una pantalla para subir este JSON. La alternativa sin consola para la estructura es crear manualmente las categorías y revisar los catálogos como se explica a continuación.

8. Cargar la estructura desde Moodle: alternativa manual

  1. Usar esta vía si no se va a ejecutar la importación inicial por consola. Mantener las dos raíces separadas de otros proyectos.
  2. En Cursos → Administrar cursos y categorías, seleccionar Biblioteca y crear sus subcategorías con Añadir categoría.
  3. Utilizar Inventario_estructura_Orange.csv como lista de comprobación. Crear primero los padres y después sus hijos; seleccionar explícitamente Categoría padre en cada alta.
  4. Reproducir el árbol aprobado, no solo los nombres. El orden de las filas del inventario permite crear padres antes que hijos. Comprobar el orden visible y ajustarlo desde la gestión de categorías si hace falta.
  5. En Formaciones crear Formación inicial y Formación continua debajo de su raíz.
  6. Después de configurar y acceder al portal, usar Administración Orange → Gestionar categorías para crear las categorías de Incidencias y Comunicados en sus secciones correctas.
  7. Revisar los estados e impactos desde Estados e impactos. Si se utilizó el JSON, no volver a crear estos mismos elementos.

En este contexto, los directorios de Biblioteca y Formaciones son categorías de Moodle almacenadas en la base de datos. No son carpetas del servidor que se creen con mkdir. Copiar local/orangeportal y theme/orange no construye ese árbol.

La referencia entregada contiene CENTREX como nodo inicial, sin inventar procesos debajo. Si el árbol aprobado en pre difiere del archivo de octubre, documentar y aplicar la diferencia antes de la apertura.

9. Revisar estados, impactos y prioridad crítica

  1. Entrar con el administrador Orange o un perfil con local/orangeportal:manageoptions.
  2. Abrir Estados e impactos y revisar cada tipo por separado.
  3. Editar nombres y activación según lo aprobado. Para Crítico, editar la opción de código critical existente en lugar de crear otra con el mismo nombre.
  4. Comprobar que queda al menos un estado activo no cerrado y los impactos necesarios para publicar.
  5. Registrar la configuración final como parte de la entrega.

En una instalación nueva sin JSON se muestran los valores predeterminados del plugin. La presencia de un nombre en pantalla no demuestra que coincida con el catálogo aprobado; revisar códigos, activación y cierre.

10. Cohorte Orange, tema y configuración del portal

  1. Mantener el tema corporativo y la portada general del campus. No seleccionar Orange como tema predeterminado global.
  2. En Usuarios → Cuentas → Cohortes, crear una cohorte de sistema Usuarios Orange, o identificar la existente. Puede usarse Número ID orange_portal_users.
  3. En Apariencia → Temas → Ajustes de temas, habilitar Permitir temas de cohortes. Revisar primero si hay otras cohortes con temas guardados que puedan activarse con este ajuste.
  4. Editar la cohorte Usuarios Orange y seleccionar Orange en su campo de tema forzado.
  5. En Administración del sitio → Portal Orange → Configuración Orange, seleccionar la cohorte de audiencia y escribir los IDs numéricos de Biblioteca y Formaciones de producción.
  6. Elegir Biblioteca como sección de entrada si esa es la opción aprobada. Revisar alertas automáticas de formación, que son independientes del envío de Teams.
  7. Activar el portal y guardar desde esa página para ejecutar sus validaciones y sincronizaciones. Evitar cambiar raíces/audiencia con SQL o copiar config_plugins de otro ambiente.
  8. En Apariencia → Temas → Orange revisar logo y personalizaciones aprobadas. Cerrar sesión y entrar con una cuenta Orange y otra ajena para comprobar el aislamiento.
/admin/settings.php?section=local_orangeportal

La pertenencia a Usuarios Orange da acceso al entorno Orange; el rol determina qué se puede hacer. Cambiar el nombre o el prefijo de una cuenta no la convierte en Orange. Un usuario de varias cohortes con temas distintos requiere revisión de la prioridad de temas.

No incorporar usuarios finales a la cohorte antes de completar la configuración y la validación del contenido. Si producción ya tenía Orange, conservar su cohorte y sus raíces salvo un cambio planificado.

11. Primer administrador Orange y perfiles de trabajo

  1. El administrador general crea o identifica una cuenta individual de administración Orange desde Usuarios → Cuentas. No reutilizar una cuenta administradora global para probar el aislamiento.
  2. Añadir la cuenta a Usuarios Orange. Con el portal y raíces configurados, asignarle Administrador de Orange desde Usuarios → Permisos → Asignar roles del sistema.
  3. No asignarle Administrador del sitio ni Gestor global. El plugin crea orange_administrador y aplica su rol de contenidos en las raíces Orange.
  4. Entrar con la cuenta y comprobar Usuarios Orange, Colectivos Orange, contenido e informes. La configuración general de Teams debe seguir reservada al administrador general.
  5. Para Formación, Coordinación y Calidad, importar o comparar las definiciones por nombre corto desde Usuarios → Permisos → Definir roles. Utilizar los XML y la matriz del paquete; no duplicar roles existentes.
  6. Asignar cada rol a la persona real de producción en el contexto indicado. Los XML no trasladan las asignaciones de pre.
Perfil / rolAsignación y alcance
AgentePertenencia a Usuarios Orange y matrículas Estudiante en sus formaciones. Sin gestión ni exportación de seguimiento.
Formador / orange_publicadorRol del portal en Sistema: gestionar publicaciones, estados y seguimiento según definición. Creación de cursos/categorías solo en raíces Orange; edición nativa en sus cursos.
Coordinación / orange_seguimientoConsulta del portal en Sistema, limitada a los colectivos de pertenencia. Sin publicar ni cambiar incidencias.
Calidad / orange_calidadConsulta separada de Coordinación. No conceder notas por defecto.
Administrador / orange_administradorAdministración Orange en Sistema y contenidos en sus raíces mediante los roles técnicos del plugin. No administración general del campus.

Los seis XML de referencia a importar o revisar son orange_publicador, orange_seguimiento, orange_calidad, orange_consulta_formativa, orange_creadorcontenidos y orange_gestorcategorias. Los roles de creación y categorías se asignan solo en las raíces Orange. La edición de cursos existentes requiere el rol nativo autorizado en esos cursos; para cursos nuevos Moodle asigna al creador el rol configurado en el campus.

orange_consulta_formativa contiene permisos para notas e intentos. Asignarlo solo a responsables autorizados y en categorías/cursos aprobados; no darlo automáticamente a Calidad. Los permisos se suman si una persona tiene varios roles.

No importar encima de los roles técnicos creados por el instalador para resolver diferencias de nombres. Mantener los nombres cortos y revisar las definiciones. El rol orange_autorrecursos lo gestiona el plugin, no necesita copiar tablas ni asignarse a todos los usuarios.

12. Colectivos, centros y carga de usuarios

  1. En Colectivos Orange crear los grupos de destinatarios y centros aprobados, por ejemplo un colectivo por centro. Son cohortes Moodle; no hay subcohortes jerárquicas.
  2. En Usuarios Orange crear las cuentas nuevas o utilizar Importar agentes desde CSV. La importación Orange crea agentes, no formadores ni coordinadores.
  3. Preparar CSV UTF-8 con las cabeceras de la plantilla. El mínimo requerido es username, firstname, lastname, email y password; idnumber, cohorts y courses son opcionales.
  4. Revisar la ayuda del importador y seleccionar colectivos y cursos del ambiente de producción. Utilizar la previsualización antes de confirmar la carga.
  5. Para cuentas ya existentes del campus y roles privilegiados, usar la administración general de Moodle y añadir su pertenencia a Orange. No crear cuentas duplicadas para forzar una importación.
  6. Validar con una cuenta importada el primer acceso, cambio de contraseña, tema y cursos disponibles.
username;firstname;lastname;email;password;idnumber;cohorts;courses

Los identificadores de colectivos y cursos deben corresponder a producción. Para varias asignaciones o campos opcionales, seguir el formato que explica el icono de ayuda de la versión instalada; no copiar IDs de pre. La importación permite seleccionar varias formaciones existentes, no obliga a matricular una persona cada vez.

Usar correos y mecanismos de entrega de credenciales aprobados para producción. Una dirección ficticia puede impedir recuperación de contraseña y comunicaciones. La pertenencia a destinatarios no sustituye una matrícula de curso.

Incidencia o comunicadoRecrear datos, destinatarios y recursos desde Orange. El JSON de categorías no migra publicaciones ni su seguimiento.
  1. En Biblioteca elegir la categoría exacta de la matriz. Añadir Archivo, Página, URL, Área de texto y medios u otro recurso nativo. No subir archivos directamente a moodledata.
  2. Revisar Usuarios individuales, Colectivos Orange y Grupos de cursos Orange. Guardar inicialmente sin Visible para sus destinatarios y sin Avisar por Teams.
  3. En Formaciones crear los cursos debajo de Formación inicial o Formación continua. Preparar sus secciones o colecciones y añadir recursos y actividades.
  4. Matricular a los usuarios existentes o utilizar sincronización de cohorte autorizada. Para una nueva edición, copiar el curso sin trasladar resultados de alumnos de la edición anterior.
  5. Si se usa .mbz, hacer copia desde el curso origen y restaurar en la categoría de producción correcta, sin usuarios de prueba ni sus intentos/notas. Mantener el curso destino oculto mientras se revisa.
  6. Después de restaurar, abrir Editar en cada formación y documento: comprobar destinatarios, matrículas, visibilidad, disponibilidad nativa, grupos y vínculos. La copia nativa no garantiza trasladar las reglas personalizadas, referencias e histórico de Orange.
  7. Probar documentos embebidos, archivos, URLs externas, cuestionarios y calificaciones con un agente autorizado antes de publicar.

Las copias .mbz y el JSON de catálogos no son una migración completa de lecturas, incidencias, comunicados o trazabilidad del plugin. Conservar un histórico existente entre ambientes requiere un procedimiento específico aprobado; no sustituir por copiar tablas o toda la base de datos sobre producción.

No marcar Teams en cada documento de una carga inicial salvo que se quiera realmente avisar por cada uno. Los cursos deben empezar ocultos durante la preparación; al copiar una edición nativa revisar la opción Ocultar.

14. Configurar la ruta de PHP CLI

Esta ruta permite lanzar tareas desde la interfaz web. Sistemas debe identificar el ejecutable PHP utilizado por el servidor de Moodle de cada ambiente. La consulta se realiza en el entorno que ejecuta Moodle y con el usuario de servicio correspondiente.

  1. Solicitar acceso a Sistemas para revisar el servidor de preproducción o producción correspondiente.
  2. Sistemas ejecuta command -v php en ese servidor. Si existe aislamiento de procesos o varios nodos, debe comprobar la ruta dentro del entorno de ejecución de Moodle y en los nodos que ejecuten tareas.
  3. Copiar la ruta devuelta. Puede ser /usr/bin/php, /usr/local/bin/php u otra. Debe corresponder a la versión PHP compatible que ya utiliza ese campus.
  4. Entrar como administrador general en Administración del sitio → Servidor → Rutas del sistema.
  5. En Ruta hacia PHP CLI pegar únicamente la ruta completa obtenida, sin argumentos ni comillas.
  6. Guardar cambios. Comprobar con Sistemas que el usuario del servidor web pueda ejecutar ese archivo.
  7. Repetir la comprobación en producción: no asumir que tiene la misma ruta que preproducción.
command -v php

Ruta directa de ajustes: /admin/settings.php?section=systempaths. Las rutas web de este manual se añaden al dominio del campus correspondiente.

Ejemplo: si el comando devuelve /usr/bin/php, escribir exactamente /usr/bin/php en Ruta hacia PHP CLI. No copiar ese ejemplo sin comprobar la salida real.

Si command -v php no devuelve nada, Sistemas debe localizar el ejecutable PHP CLI instalado y comprobar los permisos y el PATH del usuario de servicio. Configurar esta ruta no instala PHP ni modifica la versión utilizada por Moodle.

15. Configurar el servicio de Teams desde Moodle

  1. Entrar con un administrador general de Moodle.
  2. Abrir Administración del sitio → Portal Orange → Mensajería Teams.
  3. En URL del servicio Power Automate pegar la URL HTTPS completa del disparador proporcionada para ese ambiente, incluida su firma. No usar los enlaces de ejemplo de este manual.
  4. Seleccionar los tipos que deben avisar: Incidencias, Comunicados, Biblioteca y Formaciones.
  5. Revisar Avisar de nuevas publicaciones y Avisar de modificaciones de contenido. Ambas opciones deben estar activas si se quieren cubrir altas y modificaciones.
  6. Marcar Activar envíos a Teams y guardar cambios.
  7. Revisar el Estado de la integración: último intento, último resultado y última petición aceptada. Ese estado es global, no el historial de una publicación concreta.
/admin/settings.php?section=local_orangeportal_teams

Guardar estos ajustes no envía una prueba ni recorre publicaciones antiguas. La instalación nueva tiene el servicio desactivado y la URL vacía; una actualización conserva la configuración existente.

La URL firmada es una credencial: compartirla solo con quienes administran el flujo. Los registros ampliados muestran el destino sin parámetros de URL y ocultan firmas y tokens identificables.

16. Comprobar el cron: ejecución automática

Configurar PHP CLI y configurar cron son dos tareas distintas. La primera permite ejecutar desde la web; cron procesa automáticamente las tareas pendientes. Los avisos esperan al menos un minuto desde el guardado y después dependen de cuándo los recoja Moodle.

  1. Pedir a Sistemas que identifique el programador de tareas existente del campus y el usuario que lo ejecuta: cron, temporizador o planificador de la infraestructura.
  2. Confirmar que ejecuta admin/cli/cron.php de la instalación Moodle correcta cada minuto. Revisar la ruta completa de PHP, la raíz de Moodle, los permisos y las variables de entorno.
  3. Revisar la configuración existente antes de añadir nada. Si el campus ya procesa tareas, aprovechar el cron de esa instalación.
  4. Revisar la última ejecución y la salida del cron. Una salida sin errores del servidor web no demuestra que cron funcione.
  5. En instalaciones con varios nodos, comprobar con Sistemas qué nodo o servicio procesa las tareas y que utiliza el mismo código y configuración del campus.
  6. Con un aviso autorizado en la cola, comprobar que se procesa automáticamente sin pulsar Ejecutar desde la web.

Ejemplo de entrada para el crontab del usuario de servicio, solo si las rutas reales son esas. Sistemas debe adaptarla y conservar la política habitual de registro de salida del campus:

* * * * * /usr/bin/php /var/www/moodle/admin/cli/cron.php

Este es un ejemplo de configuración, no una orden para pegar en la consola. Sustituir /usr/bin/php por la ruta confirmada y /var/www/moodle por la raíz real. No crear un segundo cron si ya existe uno para ese campus.

Si se requiere una ejecución puntual desde el servidor, Sistemas puede utilizar el siguiente ejemplo con el usuario y las rutas reales:

/usr/bin/php /var/www/moodle/admin/cli/cron.php --keep-alive=0

La opción --keep-alive=0 evita la espera adicional al terminar las tareas. Sin esa opción, Moodle 4.5 mantiene por defecto el proceso hasta tres minutos comprobando nuevas tareas; una tarea activa puede tardar más.

Ejecutar cron procesa tareas pendientes de todo el campus y puede enviar mensajes reales. Para comprobar un único aviso, utilizar la tarea concreta de Teams desde la interfaz.

Anotar dónde conserva Sistemas la salida del cron y quién recibe las alertas de fallo. Si el cron se detiene, el portal puede seguir funcionando mientras los avisos se acumulan.

También puede ejecutarse una vez desde la raíz real de Moodle; este ejemplo usa /var/www/moodle:

cd /var/www/moodle
php admin/cli/cron.php --keep-alive=0

La ejecución puntual no sustituye la programación automática cada minuto.

Moodle reintenta fallos HTTP y de transporte con espera creciente, hasta cinco intentos. Las tareas omitidas no son errores HTTP y no se reenvían automáticamente. Si una tarea agota sus intentos, corregir primero la causa y revisar sus opciones de reprogramación en Moodle.

Desactivar el servicio no congela la cola: las tareas que se ejecuten mientras está desactivado pueden descartarse. Cambiar la URL tampoco traslada los pendientes al nuevo destino.

21. Si Moodle acepta la llamada pero no aparece en Teams

  1. Anotar fecha, hora y zona horaria de la ejecución Moodle, título del mensaje, código HTTP e identificador de envío.
  2. Pedir al responsable del flujo que localice esa ejecución en el historial de Power Automate.
  3. Comprobar si el disparador recibió el JSON y si las acciones posteriores terminaron correctamente.
  4. Revisar las conexiones y permisos utilizados por la acción de Teams, además del chat, canal o persona configurados.
  5. Si no hay ejecución del flujo, confirmar que Moodle llamó al ambiente y disparador correctos. Comparar dominio y ruta del log con los ajustes, sin enviar la firma en capturas.
  6. Confirmar la recepción en el destino esperado antes de considerar terminada la prueba.

HTTP 202 Accepted significa aceptación por el disparador; no confirma que la acción final de Teams haya publicado el mensaje.

Ante un timeout, el flujo podría haber recibido la petición aunque Moodle registre un fallo. La cabecera X-Orange-Event-Id es estable en los reintentos de una tarea. El flujo puede utilizarla para deduplicar; sin esa lógica no se garantiza ausencia de duplicados.

22. Validación del pase y apertura a usuarios

  1. Verificar versiones: local_orangeportal 2026111007 y theme_orange 2026102900, con Moove compatible y sin cambiar el tema general del campus.
  2. Comparar Biblioteca y Formaciones con el inventario aprobado. Revisar estados, impactos y categorías de publicaciones.
  3. Comprobar una cuenta ajena a Orange: conserva su tema y no puede abrir contenido Orange por enlace directo.
  4. Comprobar un agente Orange: solo contenido dirigido a él, sin edición ni cambio de estado de incidencias. Verificar sus matrículas y notas propias.
  5. Comprobar Formador, Coordinación, Calidad y administrador Orange con cuentas separadas. Validar lectura, escritura y seguimiento por colectivos, incluidas URLs y exportaciones.
  6. Comprobar PHP CLI guardado y cron programado cada minuto. No dar Teams por operativo mientras todas las tareas sigan pendientes.
  7. Con un mensaje de prueba autorizado, marcar Visible y Avisar por Teams, guardar, comprobar ejecución, HTTP y recepción en el destino de producción.
  8. Comprobar un guardado sin Teams marcado y un borrador: ninguno debe solicitar un aviso.
  9. Verificar el campus fuera de Orange, recibir conformidad del responsable y registrar fecha, revisión y personas que aceptan el pase.
  10. Incorporar los usuarios finales y publicar el contenido aprobado. Supervisar cola, logs y flujo tras la apertura.

Si la validación se realiza fuera de mantenimiento, mantener el acceso Orange restringido a las cuentas de validación hasta su aprobación. Sistemas conserva el procedimiento de mantenimiento del campus; no reabrir una actualización fallida.
