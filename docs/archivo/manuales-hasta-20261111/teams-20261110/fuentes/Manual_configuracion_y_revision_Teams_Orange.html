1. Antes de empezar: responsables y funcionamiento

Este manual está dirigido a los servidores de preproducción y producción. Explica cómo configurar, revisar y diagnosticar los avisos de Microsoft Teams del portal Orange. Está basado en Moodle 4.5.1 y local_orangeportal 2026111006, revisión 9ea45bb, a fecha 10 de noviembre de 2026.

ResponsableQué necesita hacer
Administrador general de MoodleConfigurar la URL y los tipos de aviso, PHP CLI y los registros de tareas. Requiere moodle/site:config.
SistemasCopiar el plugin, ejecutar la actualización, identificar PHP y mantener el cron y la conectividad HTTPS.
Formador o gestor autorizadoGuardar contenido visible y marcar Avisar por Teams al guardar cuando corresponda.
Responsable de Power Automate / TeamsMantener el flujo y sus conexiones, elegir el destino y revisar la entrega del mensaje.

El perfil Administrador Orange no concede por sí solo acceso a la configuración general de Moodle ni a la URL del servicio.

Recorrido del aviso: guardar contenido visible con Teams marcado → tarea pendiente en Moodle → ejecución por cron o por un administrador → POST HTTPS a Power Automate → publicación del mensaje por el flujo en Teams.

Los destinatarios de Moodle controlan quién puede consultar el contenido. No se convierten automáticamente en destinatarios de Teams: el chat, persona o canal se configura en el flujo. Los enlaces siguen requiriendo autenticación y permisos Orange.

2. Instalar o actualizar la versión necesaria

  1. Sistemas guarda una copia de la carpeta actual del plugin y de la base de datos del ambiente.
  2. Copiar la carpeta completa moodle/local/orangeportal del proyecto en local/orangeportal dentro de la instalación de Moodle del servidor.
  3. Comprobar que el archivo final es /var/www/moodle/local/orangeportal/version.php si esa es la raíz real de Moodle. Evitar una carpeta orangeportal anidada dentro de otra.
  4. Desde la raíz de Moodle ejecutar los comandos siguientes con el usuario de servicio que utilice ese servidor.
  5. En Administración del sitio → Plugins → Vista general de plugins, verificar Portal Orange / local_orangeportal, versión 2026111006.
cd /var/www/moodle
php admin/cli/upgrade.php --non-interactive
php admin/cli/purge_caches.php

/var/www/moodle es el ejemplo usado en pre. Sustituirlo por la ruta real si es diferente. Para esta revisión no cambia theme/orange. No copiar config.php, .env, moodledata ni la base de datos de otro ambiente.

Si pre ya tiene 2026111005, la revisión 2026111006 solo añade diagnóstico y no crea tablas. Si tiene una versión anterior, el actualizador ejecuta también las migraciones pendientes. No es necesario reimportar los catálogos por actualizar estos logs.

La URL firmada se configura por ambiente. Preproducción y producción deben mantener cada una su propia URL y su propio destino Teams.

La actualización de archivos y base de datos no completa el despliegue de Teams. Antes de darlo por terminado:

  1. Identificar PHP CLI y guardar su ruta en Moodle como indica el capítulo 3.
  2. Revisar la URL y activación de Teams del ambiente como indica el capítulo 5.
  3. Sistemas debe comprobar que el cron de esta instalación está programado cada minuto; si ya existe, no crear otro. Si falta, configurarlo con las rutas y el usuario reales como indica el capítulo 4.
  4. Tras revisar la configuración del ambiente, se puede ejecutar una comprobación puntual desde la raíz de Moodle con el comando siguiente.
  5. Confirmar que las siguientes tareas se procesan automáticamente y consultar su registro. Si todas siguen pendientes por falta de cron, la integración no queda operativa.
php admin/cli/cron.php

Esta ejecución procesa tareas pendientes de todo el campus y puede enviar mensajes reales. Ejecutarlo una vez no programa el cron: además debe quedar configurada su ejecución automática cada minuto. Para un único aviso, puede ejecutarse solo su tarea desde Moodle.

3. Configurar la ruta de PHP CLI

Esta ruta permite lanzar tareas desde la interfaz web. Sistemas debe identificar el ejecutable PHP utilizado por el servidor de Moodle de cada ambiente. La consulta se realiza en el entorno que ejecuta Moodle y con el usuario de servicio correspondiente.

  1. Solicitar acceso a Sistemas para revisar el servidor de preproducción o producción correspondiente.
  2. Sistemas ejecuta command -v php en ese servidor. Si existe aislamiento de procesos o varios nodos, debe comprobar la ruta dentro del entorno de ejecución de Moodle y en los nodos que ejecuten tareas.
  3. Copiar la ruta devuelta. Puede ser /usr/bin/php, /usr/local/bin/php u otra. Debe corresponder a la versión PHP compatible que ya utiliza ese campus.
  4. Entrar como administrador general en Administración del sitio → Servidor → Rutas del sistema.
  5. En Ruta hacia PHP CLI pegar únicamente la ruta completa obtenida, sin argumentos ni comillas.
  6. Guardar cambios. Comprobar con Sistemas que el usuario del servidor web pueda ejecutar ese archivo.
  7. Repetir la comprobación en producción: no asumir que tiene la misma ruta que preproducción.
command -v php

Ruta directa de ajustes: /admin/settings.php?section=systempaths. Las rutas web de este manual se añaden al dominio del campus correspondiente.

Ejemplo: si el comando devuelve /usr/bin/php, escribir exactamente /usr/bin/php en Ruta hacia PHP CLI. No copiar ese ejemplo sin comprobar la salida real.

Si command -v php no devuelve nada, Sistemas debe localizar el ejecutable PHP CLI instalado y comprobar los permisos y el PATH del usuario de servicio. Configurar esta ruta no instala PHP ni modifica la versión utilizada por Moodle.

4. Comprobar el cron: ejecución automática

Configurar PHP CLI y configurar cron son dos tareas distintas. La primera permite ejecutar desde la web; cron procesa automáticamente las tareas pendientes. Los avisos esperan al menos un minuto desde el guardado y después dependen de cuándo los recoja Moodle.

  1. Pedir a Sistemas que identifique el programador de tareas existente del campus y el usuario que lo ejecuta: cron, temporizador o planificador de la infraestructura.
  2. Confirmar que ejecuta admin/cli/cron.php de la instalación Moodle correcta cada minuto. Revisar la ruta completa de PHP, la raíz de Moodle, los permisos y las variables de entorno.
  3. Revisar la configuración existente antes de añadir nada. Si el campus ya procesa tareas, aprovechar el cron de esa instalación.
  4. Revisar la última ejecución y la salida del cron. Una salida sin errores del servidor web no demuestra que cron funcione.
  5. En instalaciones con varios nodos, comprobar con Sistemas qué nodo o servicio procesa las tareas y que utiliza el mismo código y configuración del campus.
  6. Con un aviso autorizado en la cola, comprobar que se procesa automáticamente sin pulsar Ejecutar desde la web.

Ejemplo de entrada para el crontab del usuario de servicio, solo si las rutas reales son esas. Sistemas debe adaptarla y conservar la política habitual de registro de salida del campus:

* * * * * /usr/bin/php /var/www/moodle/admin/cli/cron.php

Este es un ejemplo de configuración, no una orden para pegar en la consola. Sustituir /usr/bin/php por la ruta confirmada y /var/www/moodle por la raíz real. No crear un segundo cron si ya existe uno para ese campus.

Si se requiere una ejecución puntual desde el servidor, Sistemas puede utilizar el siguiente ejemplo con el usuario y las rutas reales:

/usr/bin/php /var/www/moodle/admin/cli/cron.php --keep-alive=0

La opción --keep-alive=0 evita la espera adicional al terminar las tareas. Sin esa opción, Moodle 4.5 mantiene por defecto el proceso hasta tres minutos comprobando nuevas tareas; una tarea activa puede tardar más.

Ejecutar cron procesa tareas pendientes de todo el campus y puede enviar mensajes reales. Para comprobar un único aviso, utilizar la tarea concreta de Teams desde la interfaz.

Anotar dónde conserva Sistemas la salida del cron y quién recibe las alertas de fallo. Si el cron se detiene, el portal puede seguir funcionando mientras los avisos se acumulan.

5. Configurar el servicio de Teams desde Moodle

  1. Entrar con un administrador general de Moodle.
  2. Abrir Administración del sitio → Portal Orange → Mensajería Teams.
  3. En URL del servicio Power Automate pegar la URL HTTPS completa del disparador proporcionada para ese ambiente, incluida su firma. No usar los enlaces de ejemplo de este manual.
  4. Seleccionar los tipos que deben avisar: Incidencias, Comunicados, Biblioteca y Formaciones.
  5. Revisar Avisar de nuevas publicaciones y Avisar de modificaciones de contenido. Ambas opciones deben estar activas si se quieren cubrir altas y modificaciones.
  6. Marcar Activar envíos a Teams y guardar cambios.
  7. Revisar el Estado de la integración: último intento, último resultado y última petición aceptada. Ese estado es global, no el historial de una publicación concreta.
/admin/settings.php?section=local_orangeportal_teams

Guardar estos ajustes no envía una prueba ni recorre publicaciones antiguas. La instalación nueva tiene el servicio desactivado y la URL vacía; una actualización conserva la configuración existente.

La URL firmada es una credencial: compartirla solo con quienes administran el flujo. Los registros ampliados muestran el destino sin parámetros de URL y ocultan firmas y tokens identificables.

6. Solicitar un aviso al publicar o editar

  1. Abrir o crear el comunicado, incidencia, documento de Biblioteca o formación con un perfil autorizado.
  2. Completar el título y el contenido que corresponda y revisar el bloque Destinatarios.
  3. Seleccionar usuarios, colectivos o grupos Orange si se desea limitar el acceso. Sin destinatarios específicos, el acceso queda dentro de la cohorte Orange. En Formaciones, la matrícula sigue siendo independiente.
  4. Marcar Visible para sus destinatarios. Guardar como borrador no genera aviso.
  5. Marcar Avisar por Teams al guardar. Esta opción empieza desmarcada en cada edición y solo solicita el aviso de ese guardado.
  6. Guardar. Esperar al menos un minuto y el siguiente procesamiento del cron.
  7. Revisar la cola y después el registro de la tarea correspondiente.
CasoComportamiento
Visible y Teams marcadoSe solicita el aviso si el tipo y la acción están habilitados en la configuración general.
Visible sin Teams marcadoSe guarda y publica, sin solicitar ese aviso.
Borrador, oculto o retiradoNo se envía, aunque se intente marcar Teams.
Cambio solo de estado de una incidenciaNo genera aviso de Teams.
Añadir recursos dentro de una formación o un comunicadoNo avisa por sí solo; solicitarlo desde el formulario de la publicación o formación.
Lecturas, notas, finalizaciones y eliminaciónNo generan estos avisos de contenido.

Si Teams aparece deshabilitado, revisar la activación general, la URL válida y las opciones de tipo y acción.

7. Revisar pendientes y ejecutar una tarea concreta

  1. Entrar en Administración del sitio → Servidor → Tareas → Tareas ad hoc, o usar Ver cola de envíos desde Mensajería Teams.
  2. Buscar la clase local_orangeportal\task\send_teams.
  3. Anotar el ID de la tarea, la fecha prevista y los datos kind, id y action. id identifica la publicación o curso, no la tarea.
  4. Si todavía no llegó la hora prevista, esperar. Si todas siguen pendientes después de varios minutos, revisar cron.
  5. Para una comprobación manual autorizada, ejecutar únicamente la tarea de Teams que se quiera comprobar. No usar Ejecutar todo para diagnosticar un único aviso.
  6. Abrir después su registro y comprobar si realmente hubo una llamada HTTP o se omitió con un motivo.
/admin/tool/task/adhoctasks.php
Dato de la tareaSignificado
kindnotifications = Comunicado; incidents = Incidencia; library = Documento; courses = Formación.
idID del contenido al que corresponde el aviso.
actioncreated = alta o primera publicación; updated = actualización.
endpointHuella de la URL configurada; no es la URL de destino.
contenthashHuella del mensaje autorizado al guardar; no contiene el JSON legible.
generationEn formaciones identifica la publicación vigente y evita reactivar avisos retirados.

Una ejecución manual puede enviar un mensaje real al destino configurado. Completar una tarea no significa siempre enviar: también puede completarse porque ya no corresponde enviarla.

8. Leer los logs de solicitud y respuesta

  1. Abrir Administración del sitio → Servidor → Tareas → Registros de tareas.
  2. Buscar Enviar aviso Orange a Teams o la clase local_orangeportal\task\send_teams y localizar la ejecución por ID y fecha.
  3. Abrir el detalle y leer publicación, destino, JSON, respuesta HTTP y cuerpo de respuesta.
  4. Si no aparecen tareas correctas, revisar la configuración de Registro de tareas para registrar todas las ejecuciones, no solo fallos. También comprobar el período de conservación.
/admin/tasklogs.php
/admin/settings.php?section=tasklogging

Ejemplo ficticio de una ejecución aceptada. El destino real tendrá su propio dominio y ruta; los parámetros firmados no se muestran:

Teams: publicación notifications #399 · updated.
Teams: destino POST https://servicio.example.invalid/invoke (parámetros de URL ocultos).
Teams: JSON enviado: {"titulo":"Comunicado actualizado: Ejemplo","contenido":"Contenido de prueba","url":"https://campus.example.invalid/local/orangeportal/view.php?id=399"}
Teams: identificador de envío: ...
Teams: respuesta HTTP 202 (249 ms).
Teams: cuerpo de respuesta: (vacío)
Teams: HTTP request accepted.
LíneaQué demuestra
Destino POSTServidor y ruta utilizados; consultar la configuración para la URL firmada completa.
JSON enviadoLos campos titulo, contenido y url del aviso concreto; sus valores proceden de la publicación.
Respuesta HTTPCódigo devuelto y duración de la petición.
Cuerpo de respuestaTexto o JSON devuelto por el servicio, depurado y limitado a 4.000 caracteres.

Los detalles ampliados requieren 2026111006 y solo existen para ejecuciones nuevas. Los detalles que no se guardaron en ejecuciones anteriores no pueden reconstruirse. No hace falta reenviar un mensaje ya entregado solo para obtener un registro nuevo.

9. Interpretar errores y tareas omitidas

Resultado o síntomaQué revisar
No se encuentra PHP CLIEjecutar command -v php en el entorno de ejecución del servidor Moodle correcto y guardar esa ruta en Rutas del sistema.
Todas las tareas pendientesHora prevista, cron activo, última ejecución y configuración de PHP CLI para ejecuciones web.
HTTP 200, 201 o 202La llamada fue aceptada por el servicio. Comprobar la entrega posterior en Power Automate. Un cuerpo vacío es válido.
HTTP 400Leer el cuerpo del error; revisar el contrato JSON y la validación del disparador.
HTTP 401 o 403Comprobar la URL completa, su firma y los requisitos de acceso del flujo.
HTTP 404Comprobar ruta del disparador, ambiente y que el flujo siga existiendo.
HTTP 429 o 5xxPosibles límites o fallo del servicio. Revisar el flujo y los reintentos de Moodle.
HTTP 3xxLa integración no sigue redirecciones; usar la URL HTTPS directa del disparador.
HTTP 0 / error de transporteLeer el detalle; Sistemas revisa DNS, salida HTTPS, certificados, proxy y restricciones HTTP de Moodle. No desactivar TLS para resolverlo.
Integración, tipo o acción desactivadosRevisar las casillas del panel y la validez de la URL.
La URL configurada cambióLa tarea antigua se descarta. Revisar el destino nuevo y solicitar un nuevo aviso guardando la publicación si corresponde.
Publicación anterior de la formaciónEl curso se retiró o volvió a publicar; la tarea corresponde a una generación anterior.
Contenido no publicado, visible o disponibleComprobar borrador, retirada, eliminación y visibilidad de curso, categoría y recurso.
Contenido cambió después del guardadoLa tarea antigua no anunciará una edición silenciosa posterior. Solicitar un nuevo aviso desde el contenido vigente si corresponde.

Moodle reintenta fallos HTTP y de transporte con espera creciente, hasta cinco intentos. Las tareas omitidas no son errores HTTP y no se reenvían automáticamente. Si una tarea agota sus intentos, corregir primero la causa y revisar sus opciones de reprogramación en Moodle.

Desactivar el servicio no congela la cola: las tareas que se ejecuten mientras está desactivado pueden descartarse. Cambiar la URL tampoco traslada los pendientes al nuevo destino.

10. Si Moodle acepta la llamada pero no aparece en Teams

  1. Anotar fecha, hora y zona horaria de la ejecución Moodle, título del mensaje, código HTTP e identificador de envío.
  2. Pedir al responsable del flujo que localice esa ejecución en el historial de Power Automate.
  3. Comprobar si el disparador recibió el JSON y si las acciones posteriores terminaron correctamente.
  4. Revisar las conexiones y permisos utilizados por la acción de Teams, además del chat, canal o persona configurados.
  5. Si no hay ejecución del flujo, confirmar que Moodle llamó al ambiente y disparador correctos. Comparar dominio y ruta del log con los ajustes, sin enviar la firma en capturas.
  6. Confirmar la recepción en el destino esperado antes de considerar terminada la prueba.

HTTP 202 Accepted significa aceptación por el disparador; no confirma que la acción final de Teams haya publicado el mensaje.

Ante un timeout, el flujo podría haber recibido la petición aunque Moodle registre un fallo. La cabecera X-Orange-Event-Id es estable en los reintentos de una tarea. El flujo puede utilizarla para deduplicar; sin esa lógica no se garantiza ausencia de duplicados.

11. Prueba completa y parte para Sistemas

  1. Confirmar versión del plugin, URL del ambiente, tipos/acciones habilitados, PHP CLI y cron.
  2. Acordar una publicación y un destino de prueba con las personas responsables: esta validación puede publicar un mensaje real.
  3. Crear un comunicado de prueba para los destinatarios Orange previstos y marcar Visible para sus destinatarios y Avisar por Teams al guardar.
  4. Guardar, anotar título y hora, y comprobar la tarea en la cola.
  5. Esperar al procesamiento o ejecutar solo esa tarea de forma autorizada.
  6. Abrir el log: verificar destino, JSON, respuesta HTTP y cuerpo.
  7. Verificar la ejecución de Power Automate y la recepción en Teams.
  8. Editar la publicación sin marcar Teams y comprobar que ese guardado no solicita un nuevo aviso.
  9. Guardar un borrador sin publicar y comprobar que tampoco solicita un aviso.
  10. Documentar el resultado; retirar el contenido de prueba cuando deje de ser necesario.
